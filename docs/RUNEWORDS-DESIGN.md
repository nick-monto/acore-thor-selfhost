# Runewords

Physical rune items drop from creatures along a level ladder. A player who holds an exact
pattern of those runes in one container — the backpack, or one bag — is granted that word's
auras, and loses them the moment the pattern breaks. Runes never enter a socket and nothing
is written to equipment, so a word stacks on top of the gems and enchants the character
already has.

## Why a pattern in the bags

Three constraints shaped this, and each one closed a door.

**It must stack with gems and enchants.** The obvious carrier for a socketable rune is a
socket: rune items become gems through `item_template.gemproperties`, and the core applies a
gem's enchant on insert (`Handlers/ItemHandler.cpp:1355-1372`). But a socket holds one thing,
so a rune in a socket *is* a gem's replacement, not an addition. Stacking therefore rules
out the socket.

**The enchantment channel cannot be made both free and stacked.** A container's twelve
enchant slots look uncontested — bags take no player enchant, no gems and no rolled suffix —
but they never reach the player:

```
bool Item::IsEquipped() const { return !IsInBag() && m_slot < EQUIPMENT_SLOT_END; }
```
`Item.cpp:792`, with `EQUIPMENT_SLOT_END == INVENTORY_SLOT_BAG_START == 19` (`Player.h:681`,
`:686`). A bag in bag slot 19–22 is not `IsEquipped()`, and `Player::ApplyEnchantment` returns
on its first line because of it (`Entities/Player/PlayerStorage.cpp:4416`). The
`_ApplyAllItemMods` loop does run over bag slots (`Player.cpp:7810-7824`), but the enchant
call inside it is a no-op there; the loop covers item-set accounting and
`ApplyItemEquipSpell`. **[V]** measured by the compile-time constants, not by a test.

**The geometry has to be visible to the player.** The client draws every bag four columns
wide and fills it row-major:

```lua
NUM_CONTAINER_COLUMNS = 4;                     -- Interface\FrameXML\ContainerFrame.lua:8
local rows = ceil(size / columns);             -- :369
if ( mod((i-1), columns) == 0 ) then ...       -- :525  a new row every fourth slot
```

So a cell is `row = (n-1) div 4`, `col = (n-1) mod 4`, slot 1 is top-left, and adjacency is
meaningful: `n±1` along a row, `n±4` down a column. A word can therefore be a shape, and the
player can see the shape they built. `CONTAINER_FIELD_SLOT_1` is 72 fields
(`Entities/Object/Updates/UpdateFields.h:80`), so eighteen rows of four is the tallest grid a
pattern may address. **[V]** read from the client's own FrameXML and the core's field table.

The result: runes live in ordinary inventory slots, cost inventory slots, and the auras come
from stock spells cast on the player. Nothing displaces a gem, an enchant or a suffix, and no
item field is spent to make room.

## Ruleset

1. Thirty-three runes (El through Zod) drop from creatures, one ladder rung at a time: El from
   level 1, Zod from level 80, spread evenly between.
2. A rune is an ordinary item — class 15, not equippable, **not stackable**, tradable, and worth
   coin that rises with its rarity. It occupies an inventory slot, not a bag slot. One rune per
   slot: the roll belongs to the item instance, and a stack would carry one roll for the whole
   pile.
3. Holding a word's runes in the shape the word describes, inside **one** container, grants
   the word. The longest match wins, then the lowest word id.
4. Each rune instance rolls 1..100 when it is first seen. A word is worth the **average** of its
   rune rolls, rounded half up and floored by the word's own minimum; the average scales the
   borrowed spell's basepoints.
5. Breaking the pattern removes the auras on the next scan. Death removes them too, unless
   `Runewords.ApplyWhenDead = 1`.
6. Nothing is announced when a word breaks; forming one sends a chat line naming the word and
   the percentage its runes averaged to.

## Mechanisms, with the evidence

### The word table

`runeword_words` is generated by `scripts/runewords/gen_runewords.py` and applied from the
custom SQL slot (`sql/custom/db_world/runewords_20_words.sql`). One row per word:

| Column | Meaning |
|---|---|
| `id`, `name` | identity, and the tie-break order |
| `pattern` | ordered `row:col:entry` triples — the shape, and the rune expected in each cell |
| `spell_1..3` | the stock spell ids granted while the word holds |
| `scale` | percent of the stock spell's own basepoints |
| `min_pct` | floor on the rune-roll average |
| `required_level` | player level gate |

Encoding the cells and the runes together in one column means the shape and its runes cannot
drift apart; there is no parallel array to keep in step.

### The words, and the spells they borrow

Twenty-four words, 2 to 6 cells each, and **every one of the 33 runes is named by at least one
of them** — `gen_runewords.py` refuses to write a table that leaves a rune out, because a rune
no word uses is an item whose only purpose is its price (the add-on says exactly that on its
tooltip). The generator also refuses an unconnected path, a cell off the 4-wide grid, a rune
outside the ladder, and a `min_pct` outside 1..100.

Effects are stock auras, never authored spells, and only four families are drawn from:

| Family | Aura | What it does | Amounts used |
|---|---|---|---|
| `Increased <stat> NN` | 29 (MOD_STAT) | flat Str/Agi/Sta/Int/Spi | 12 to 46 |
| `Attack Power NN` | 99 (MOD_ATTACK_POWER) | flat attack power | 40, 60 |
| `Increase Spell Dam NN` | 13 (MOD_DAMAGE_DONE) | flat spell damage | 23, 40 |
| `Thrash`, `Bruise`, `Thick Skin`, `Fel Lightning` | 42 (PROC_TRIGGER_SPELL) | a weapon proc | the spell itself |

Every pick was read out of the client's own `Spell.dbc` (`data/dbc/Spell.dbc`, the file the
server loads) and satisfies the same four conditions, which are what make a stock spell safe to
serve every roll: the aura is permanent (`SpellDuration.dbc` duration `-1`, decode it as
`4294967295`), its value is deterministic (`EffectDieSides` 1, `EffectRealPointsPerLevel` 0), its
`EffectBasePoints` is positive, and it targets the caster (`ImplicitTargetA` 1). Anything else —
a finite duration, a die roll, a level term — is skipped with a log line rather than granted for
a minute.

Gates are the rarest rune's own availability: Nadir (Nef, Tir) opens at 8, Heart of the Oak
(Ko, Vex, Pul, Thul) at 63, Breath of the Dying (Vex, Hel, El, Eld, Zod, Eth) at 80. A word is
worth the average roll of its runes, so the top of the ladder buys a wider effect, not a bigger
multiplier: Call to Arms, Doom and Breath of the Dying each grant three auras.

### Matching

The matcher walks the rune cells of one container, and for each rune tries every cell of the
word as the position that rune could occupy. Translating by `slot - offset(cell)` gives a
candidate origin; the word holds if every cell of the pattern lands inside the container and
holds the expected entry. This is position-independent — nothing anchors a shape to a corner —
and it is a handful of comparisons per rune, so the scan is dominated by walking the bag, not
by matching. Matching is scoped to one container because bag windows keep no order among
themselves: the server sees `(bag, slot)` pairs, and the client floats each bag window
wherever the player drags it, so "in order across bags" would be neither visible nor stable.

Ties resolve to the longest word, then the lowest id, so the outcome does not depend on the
order containers and slots happen to be walked in.

### Variance

The roll lives in the characters database, keyed by the item instance (item instances live in
`acore_characters.item_instance`, so a world table cannot key them):

```sql
CREATE TABLE IF NOT EXISTS `character_runeword_rune` (
  `itemGuid` BIGINT UNSIGNED NOT NULL,
  `roll`     TINYINT UNSIGNED NOT NULL DEFAULT 1,
  `rolled`   INT UNSIGNED NOT NULL DEFAULT 0,
  PRIMARY KEY (`itemGuid`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

It is created programmatically at startup (`Runewords::EnsureSchema`), not by module SQL: on
this fork a failing module SQL file aborts the whole worldserver boot, which is the reason
`mod-survivor` creates its tables the same way.

The roll is assigned **lazily** — the first time a rune item is seen in a bag — and never
again, so it survives the auction house, the mail and a reinstall of the module, and no
item-creation hook is needed for drops, crafts, quest rewards or `.additem`.

A word's percentage is `max(min_pct, round(mean(roll over its runes)))`: one poor rune costs
its share of the word rather than the whole thing, two perfect runes are worth more than one
perfect and one poor, and the floor keeps an all-1s word from being worthless.

### Rarity and value

A rune's rarity is its ladder position, so the quality colour says the same thing twice: the
rune that has just become available is the rarest row in its bracket's table, and one that has
been dropping for twenty levels is the commonest thing in it. Five bands, in
`scripts/runewords/gen_runewords.py`:

| Steps | Quality | Floor price |
|---|---|---|
| 1–8 | white | 25 copper |
| 9–16 | green | 5 silver |
| 17–24 | blue | 50 silver |
| 25–30 | epic | 2 gold 50 |
| 31–33 | legendary | 12 gold |

`item_template.SellPrice` is the band floor plus a quarter of it per step inside the band, so a
later rune of the same colour is still the rarer purchase; the ladder ends at 18 gold for Zod.
The roll pays up to that price again, which no static `item_template` column can express:
`PlayerScript::OnPlayerCanSellItem` is the only point a module reaches before the core pays
(`ItemHandler.cpp` calls it, then computes `money = SellPrice * count`), so the module pays
`SellPrice * roll / 100` there and the core pays the template price after it. The hook repeats
the sell handler's own refusals - not the owner, a non-empty bag, a refundable item, the item
being looted, the gold cap - because a payout for a sale that then fails cannot be taken back.

The add-on does not need the hook to know the number: the price lands in
`Runewords_Data.lua` with the rest of the ladder, and the rune tooltip shows the value at that
instance's roll.

### Scaling a stock spell

`SpellEffectInfo::CalcValue` takes custom basepoints in place of the DBC value and then
applies the same die roll the DBC would have (`Spells/SpellInfo.cpp:412`,
`case 1: basePoints += 1` at `:437`). The module therefore computes each effect's reference
value as `BasePoints + average die roll`, multiplies by `scale × pct`, and subtracts the
average again before casting, so the average output is exactly the stock value scaled by the
two percentages. One stock spell then serves every roll, and no spell is authored per tier.

`Player::CastCustomSpell` (`Entities/Unit/Unit.h:1688`) is what carries those values, cast
triggered so the spell has no cast time or cost; `Unit::RemoveAura(spellId)` (`:1395`) takes
them off again.

**Duration is a hard requirement.** A word's auras are granted once and re-derived only when
the pattern changes, so a spell with a finite duration would lapse a minute after the word
formed and never come back. Only spells whose duration is `-1` belong in the table
(`SpellInfo::GetDuration`, `Spells/SpellInfo.cpp:2764`), and the module refuses a finite one
at cast time with one log line per spell rather than granting something that expires. That
rules out most stock proc auras — Frost Armor, Lightning Shield and Pulverize are all
self-buffs with a duration — and leaves the permanent ones: Thrash, Bruise, Thick Skin, Fel
Lightning among 435 candidates.

### Reconcile, not events

The applied state is compared against the desired state on a per-player interval
(`PlayerScript::OnPlayerUpdate`, which the core calls from `Player::Update`,
`Entities/Player/PlayerUpdates.cpp:314`), staggered by a per-player accumulator. An unchanged
pattern costs one bag scan and no cast. A missed event — a bag swap, a mailed rune, a GM
destroy — therefore cannot leave a stale aura behind, which is the failure mode that would
matter, because a leaked aura is a permanent buff.

## Drops

A rune becomes available at a level and stays in every later bracket. Within a bracket its
weight falls as it ages — `weight = 1 + age/2`, capped at 40 — so the newest rune in a bracket
is the rarest row in its table and the top of the ladder is a chase rather than a formality.
The bracket table is referenced from one `creature_loot_template` row per creature loot id,
with a chance that rises with creature rank (2% normal, 15% boss).

Both tables are generated from the pinned core's own dumps, so the ladder follows the base
database rather than a hand-kept list; `--check` fails when the committed SQL stops matching a
fresh run.

## The client patch stays at one file

The runes borrow their icons from the base database's own gems — 142 distinct display ids
across 677 gem items — so no `ItemDisplayInfo` row is added and no art is drawn. The only
client-side requirement is one `Item.dbc` record per rune, which
`scripts/item-dbc/patch_item_dbc.py` appends from the same generated SQL that fills the
database, so the two cannot drift.

The auras are stock spells, so nothing needs a `Spell.dbc` row: reusing a spell costs a
49 MB `Spell.dbc` patch and buys nothing here. The cost of reuse is that a stock spell's
tooltip is its own static text, so a scaled word shows the stock number. That is why the
add-on, not the item tooltip, is the surface that shows the real values.

## The add-on's two halves

The add-on ships from `acore-thor-launcher` (`app/src/main/assets/runewords/`) and needs two
things the client cannot get on its own.

**The tables, generated.** `gen_runewords.py --lua <path>` writes `Runewords_Data.lua` — the
same rune ladder and word table the SQL is built from. The add-on therefore matches patterns
with the identical rule (four-wide grid, connected cells, longest then lowest id), so the
cells it highlights are the cells the server grants, with no second convention to keep in
step. Regenerating after a word changes is one flag; `--check` covers it like the SQL.

**The rolls, asked for.** A rune's 1..100 roll lives in `character_runeword_rune` and is per
instance, so the client cannot see it. The add-on sends itself one add-on whisper,
`RUNE\tsync`, and the module answers on the carrier `mod-survivor` already uses for its map
pin (`ChatHandler::BuildChatPacket`, `CHAT_MSG_WHISPER`, `LANG_ADDON`, sender = receiver):
`RUNE\tslots <bag>:<slot>:<roll>:<entry>` tokens, chunked at 200 characters because an add-on
message is one chat line. `<bag>` is the client's own numbering — 0 for the backpack, 1..4 for
the equipped bags — because that is what `GetContainerItemInfo` takes, and the server's
equipment slots 19..22 map onto it in order. The message is swallowed at
`OnPlayerCanUseChat`, so it never reaches the chat log or another handler.

Nothing is pushed unasked: rolls never change once assigned, so one sync at login and after a
bag change is the whole conversation.

One consequence of borrowing *passive* spells (`SPELL_ATTR0_PASSIVE`, which all thirteen carry):
`Aura::CanBeSaved` returns false for them (`Spells/Auras/SpellAuras.cpp:1157`), so a word's auras
are not written to `character_aura` and do not survive a relog — they are re-derived from the bags
at login, which is the design's own model. It also means they may never reach the buff bar, so the
add-on's panel is the surface of record and its aura-tooltip rewrite is only a fallback for a word
that borrows a non-passive spell.

## Configuration

| Key | Default | Meaning |
|---|---|---|
| `Runewords.Enable` | `1` | master switch; 0 removes any granted word on the next tick |
| `Runewords.SweepIntervalMs` | `1000` | rescan interval per player, floored at 200 |
| `Runewords.ApplyWhenDead` | `0` | keep a word while its holder is dead |
| `Runewords.Announce` | `1` | chat line when a word forms or changes |

`.runewords status` reports the caller's active word and every rune cell with its roll;
`.runewords list` (gamemaster) prints the loaded words; `.runewords reload` re-reads `runeword_words`
(security level `SEC_GAMEMASTER`).

## Edge cases

- **Two words match at once** (one per container): longest wins, then lowest id — deterministic.
- **A pattern at the right edge**: a flat index cannot describe a four-wide shape — index 3 is the
  right edge of a row and 4 the left edge of the next — so a placement is only accepted when every
  cell stays inside the anchor's column band. Without that, Tal on the right edge and Eth on the
  next row's left would form a word nobody drew.
- **A stack of runes from before they stopped stacking**: the stack counts as one rune for the
  pattern and carries one roll; the count is not part of the identity, and the sale hook pays the
  roll's bonus per unit in the stack.
- **A word whose pattern needs more rows than the container has**: the candidate origin is
  rejected when any cell would land outside the grid, so a small bag simply cannot host a tall
  word. A 4-wide container caps a horizontal run at four runes; longer words must turn a corner
  or run down a column.
- **A bag addon that changes the grid width**: `NUM_CONTAINER_COLUMNS` is a mutable global in
  the client's Lua, so a custom bag frame can render a different lattice than the one a pattern
  assumes. The add-on should pin it or draw its own rune panel.
- **Level gate**: a word is not considered while the player is below its `required_level`, and
  any word already applied is removed.
- **A stripped aura**: a dispel, a purge or a shapeshift can remove a granted aura without the
  pattern moving. The scan checks `HasAura` on the word's first spell and re-applies the whole
  word when it is gone, so the state self-heals without a full re-cast every interval.
- **Dead players** follow `Runewords.ApplyWhenDead`; resurrection re-applies on the next scan.
- **Module disabled**: the scan returns immediately, and switching it off takes back the auras
  already granted instead of leaving them up.
- **`runeword_words` empty**: no aura is ever cast.
- **A word that broke while its holder was offline**: aura rows are only saved for non-passive
  spells, so this cannot silently outlive the pattern — and the login path removes every spell the
  table names before it reconciles, so the bookkeeping never has to have seen it.
- **Concurrency**: `OnPlayerUpdate` runs on a map-update worker while logout and `.runewords
  reload` run on the world thread, so the word table, the per-player state and the roll cache are
  behind one recursive mutex, the same guard `mod-survivor` puts on its cache.

## Failure modes and mitigations

| Failure | Effect | Mitigation |
|---|---|---|
| A missed inventory event | stale aura (a permanent buff) | reconcile against the bags, never against events |
| A rune roll lost | the word changes strength silently | the roll is written the first time the item is seen and cached; the table is the only writer |
| Two words matching in one container | non-deterministic grant | length then id, decided in code, not by iteration order |
| A word naming a spell the client lacks | the cast does nothing visible | the module logs it once per load; spells are stock ids, so a missing one is a content error |
| A pattern naming a rune that does not exist | an unmatchable word | the generator refuses to write it |
| A bracket table nothing references | a startup log line per table | only brackets a creature actually rolls are written |
| Module SQL failing at boot | the realm does not start | the module ships no SQL; its characters table is created at startup |
